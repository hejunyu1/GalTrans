# 0011：用稳定请求身份缓存经过验证的翻译结果

- 状态：已接受
- 日期：2026-08-20

## 背景

ADR 0010 的单批次执行器在调用后端前保存 `running`，并在完成时原子保存已接受提案与检查点。
若进程在后端返回后、完成事务提交前退出，恢复会再次调用后端。对未来的付费模型，这可能产生
不必要的重复请求；而直接按批次 ID 缓存又无法区分模型、提示模板或配置变化。

GalTrans 当前没有真实 Provider、价格表或玩家工作区，因此先实现应用自有的稳定请求身份和
已验证结果缓存，不把供应商特有会话或缓存 ID 变成事实来源。

## 决定

### 请求身份

请求 schema 从 1 开始。`request_` ID 对以下规范 JSON 计算 SHA-256 摘要并保留 24 个十六进制
字符：

- 请求 schema 版本；
- 调用方显式提供的 `backend_identity`；
- 完整、有序的筛选 `TranslationBatch`。

`backend_identity` 必须是稳定、非空且有界的普通字符串。未来调用方必须让它代表提供方、模型、
提示模板、工具和所有影响输出的配置版本；任一配置变化都必须使用新 identity。它不得包含 API
密钥、访问令牌或其他凭据。

### SQLite v2 结果缓存

翻译数据库 schema 提升到 v2，新增 `translation_request_cache` 表，保存请求 ID、任务、批次、
backend identity、规范批次 JSON 和完整提案 JSON。现有 v1 和未知版本失败关闭，不自动迁移。
当前尚无 CLI 或玩家入口创建长期数据库，没有足够需求为内部测试格式增加迁移代码。

写入缓存前，每个提案必须经过当前引擎验证器，并且一个批次的所有文本段必须恰好各有一个
有效提案。相同请求 ID 的相同结果可幂等写入；不同结果不能覆盖首次缓存。读取时重新核对请求
元数据，并再次验证提案 schema、任务、批次、来源 SHA-256、目标语言和受保护标记。

### 执行顺序与恢复窗口

执行器在记录批次 `running` 后先查缓存。命中时不调用后端；未命中时调用后端、验证完整响应，
先提交缓存，再用现有事务保存已接受提案与完成检查点。

缓存和完成检查点是两个有序事务，这是有意的恢复边界。缓存可以存在而任务仍为 `running`；它
仍只是必须重新验证的结构化提案，不代表批次完成，也不获得渲染或导出权限。若进程在两次事务
之间退出，显式恢复任务后可以重用缓存而不再次调用后端。

## 推迟

本增量不实现真实模型、Provider 会话、服务端幂等键或请求查询、在途请求状态、翻译记忆、缓存
淘汰、数据库迁移、审计事件、用量和费用、预算审批、CLI/GUI 或自动导出。缓存只在同一精确任务
批次和 backend identity 下命中，不做跨任务、模糊或逐句复用。

尤其是，如果请求已到达未来的服务端，但响应在本地缓存前丢失，本地缓存无法证明服务端是否
执行或计费。该模糊失败必须由后续 Provider 边界通过供应商幂等能力、请求查询或玩家审批处理，
不能把本地结果缓存描述成完整费用去重。

## 结果

GalTrans 现在可以稳定标识一次精确后端请求，并在响应已经通过验证和持久化后安全重用它。CI
可以模拟“缓存已写、检查点未完成”的崩溃，证明重开和恢复不会重复调用确定性替身。

代价是调用方必须正确维护 backend identity，SQLite v1 文件不再可打开，并且缓存会持续增长。
这些限制在真实 Provider、玩家工作区和长期数据出现后需要通过配置摘要、迁移和淘汰策略解决。
