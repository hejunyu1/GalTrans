# 0015：把确定性质量报告绑定到已接受提案并持久化

- 状态：已接受
- 日期：2026-08-25

## 背景

ADR 0014 已定义关闭式质量报告和第一条“译文与原文未变化”检查，但报告只存在于内存。进程
关闭后如果仅保存一个调用方提供的 `clear` 或 `low_confidence` 值，数据库无法证明该结果是否
来自当前任务真正接受的提案，也无法阻止调用方把需要复核的结果伪装成 `clear`。

现有 SQLite 已经原子保存任务、完成检查点和提案正文，并能按检查点顺序恢复被接受的提案。
质量报告应绑定这些应用自有事实，而不是复制一套可独立漂移的译文或审批状态。

## 决定

### SQLite v4

翻译数据库 schema 提升为 v4，新增 `translation_quality_reports` 表。每个任务最多保存一份当前
质量报告规范 JSON，并通过外键绑定 `translation_tasks`。报告写入使用现有 `BEGIN IMMEDIATE`
事务；相同报告可以幂等保存，不同内容不能覆盖首次持久化结果。

SQLite v1、v2、v3 和未知版本继续失败关闭，不进行自动迁移。当前仍没有 CLI、玩家工作区或长期
用户数据库，尚无真实数据需要迁移；在出现用户数据前维持明确拒绝，比未经备份策略验证的静默
升级更安全。

### 只从已接受提案重新计算

只有检查点和全部批次都为 `completed` 的任务可以保存质量报告。存储层在同一事务中：

1. 重新解析数据库中的任务和完成检查点；
2. 核对每个检查点提案引用及对应提案正文的任务、批次、文本段、来源摘要、语言和内容摘要；
3. 用调用方提供的当前引擎确定性验证器重新验证每条提案；
4. 重新调用 `assess_translation_quality` 生成预期报告；
5. 只在预期报告与调用方报告完全相同时写入规范 JSON。

因此调用方不能只改 outcome、finding 或 proposal ID 后保存伪造报告。质量报告仍不授予渲染、
导出、SDK、启动或文件访问能力。

### 重开恢复与损坏检测

读取持久化报告时，存储层先按关闭式 schema 解析，再从当前数据库中的已接受提案和当前引擎
验证器重新计算。报告与任务、提案、检查集合或重新计算结果任一不一致都会失败关闭。数据库中
没有报告时返回 `None`，不会把“尚未生成”猜测为 `clear`。

## 推迟

本增量不持久化人工批准、驳回、备注或问题豁免，不增加质量规则、数值评分、语义审校、审计、
用量和费用，也不实现数据库迁移、备份、CLI、GUI、真实 Provider、网络、自动渲染、导出或启动。

## 结果

GalTrans 现在可以在进程关闭和数据库重开后恢复一份可重新证明的确定性质量报告。报告身份来自
已完成检查点真正接受的提案，而不是调用方自报状态；损坏或伪造的 `clear` 结果不会被当作可信
事实恢复。

代价是数据库版本提升到 v4，旧内部测试数据库不能直接打开；每次读取还会重新解析并验证提案。
当前任务规模和无长期用户数据的阶段下，这个保守成本小于缓存未经复核的质量结论。
