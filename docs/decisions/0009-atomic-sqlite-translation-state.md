# 0009：在输入项目之外原子保存翻译任务、检查点和已接受提案

- 状态：已接受
- 日期：2026-08-20

## 背景

ADR 0008 已定义稳定任务、批次、结构化提案和可序列化检查点，但进程退出后没有任何持久化状态。
如果提案正文和检查点中的提案 ID 分两次保存，任一步骤崩溃都可能产生“批次已完成但译文丢失”
或“译文存在但任务仍会重复执行”的不一致。直接覆盖较新的检查点还会丢失另一个执行者的进度。

V0.3 需要先让应用自有状态真正可恢复，再接真实模型、缓存或外部 Agent 会话。Python 标准库
已经提供 SQLite，当前没有引入第三方存储依赖的必要。

## 决定

### 文件和 schema 边界

`TranslationStore` 接受明确的数据库文件和只读输入项目根目录。数据库必须位于输入项目之外，
父目录必须已经存在，数据库路径不能是符号链接。创建数据库不会读取、复制或修改输入项目，
输入根目录只用于隔离检查。

新数据库使用固定 SQLite `application_id`（`GTRN`）和 `user_version = 1`，只包含：

- `translation_tasks`：任务 ID、规范 JSON 和当前检查点 JSON；
- `translation_proposals`：提案 ID、任务/批次/文本段 ID 和完整提案 JSON。

打开已有文件时必须匹配 application ID、版本、表和字段；普通 SQLite 文件、未知版本或不兼容
结构都失败关闭，不在其中创建或修改 GalTrans 表。任务、检查点和提案继续使用自身的关闭式
schema 反序列化，数据库结构不能绕过应用层版本验证。

### 初始化和恢复

任务规范与检查点以排序键、无多余空白的规范 JSON 保存。第一次初始化同时保存任务和初始
`pending` 检查点；相同任务再次初始化只返回现有检查点，不能把已开始或已完成进度重置。

数据库重开后必须重新解析任务 ID、任务内容摘要、检查点 schema 和状态不变量。已接受提案按
检查点中的批次与文本段顺序读取，并重新核对提案内容摘要和来源记录。存储层返回的仍是结构化
提案；在进入渲染或导出前，调用方必须再次使用当前引擎适配器验证目标标记。

### 原子提交和并发

所有检查点更新使用 `BEGIN IMMEDIATE` 事务和比较并交换：调用方同时提供自己读取的旧检查点与
拟写入的新检查点；数据库当前 JSON 必须仍与旧值完全相同，否则拒绝用过期状态覆盖新进度。

状态转换不能减少尝试次数、移除已接受提案或改变已完成批次。开始批次必须恰好增加一次尝试。
当批次完成时：

1. 每个新增提案先通过调用方提供的确定性引擎验证器；
2. 本次新增提案 ID 必须与新检查点新增的引用完全一致；
3. 提案正文写入后，再核对任务、批次、文本段、IR schema、来源 SHA-256、目标语言和标记记录；
4. 最后在同一事务内更新检查点。

任一步骤失败都会回滚提案插入和检查点更新。后端不能直接写数据库或自行把任务标记完成。

## 推迟

本增量不实现请求缓存、翻译记忆、审计事件、用量和费用表、预算审批、数据库迁移、备份、加密、
多进程任务调度、真实模型、CLI/GUI 工作区选择或自动导出。它也不选择玩家工作区的最终目录；
当前调用方必须明确提供输入项目之外的现有父目录。

## 结果

GalTrans 现在可以在关闭并重新打开 SQLite 数据库后恢复任务与检查点，并保证已接受提案正文和
完成状态不会只保存一半。多个执行者持有旧检查点时，后提交者会得到明确冲突而不是覆盖新状态。

代价是第一版存储 schema 有意很小，不承担缓存、费用或完整审计职责。未来增加这些表必须提升
数据库版本并定义迁移或明确拒绝策略，不能静默猜测旧结构。
