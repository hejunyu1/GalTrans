# 0019：先只读识别 Ren'Py 成品结构，再开放任何导入能力

- 状态：已接受
- 日期：2026-08-27

## 背景

V0.4.0 的玩家工作台只能处理带 `.rpy/.rpym` 的 source-only 项目，而普通玩家拿到的 Ren'Py
成品通常包含 `.rpyc`、`.rpymc` 或 `.rpa`。直接把这些扩展名当作可汉化项目会误导玩家；在尚未
定义授权、格式和隔离边界前就解包或反编译，又会扩大安全、兼容和维护风险。

下一步需要先回答一个更小且确定的问题：所选目录是否有足够证据属于 Ren'Py、当前流程能否处理、
如果不能是因为只有成品文件还是因为证据不足。这个判断必须保持输入只读，并能被后续桌面界面和
导入器稳定消费。

## 决定

新增 `inspect_renpy_compatibility` 内部接口和关闭式 v1 报告。接口接受项目根目录或其 `game`
目录，只枚举根目录启动器、`renpy`/`lib` 运行时标记，以及 `game` 下的已知路径类型：

- `game/tl` 之外的 `.rpy/.rpym` 是当前流程可使用的松散源脚本；
- `game/tl` 之外的 `.rpyc/.rpymc` 是编译脚本证据；
- `.rpa` 只作为归档路径证据，检查器不读取其内容；
- `game/tl` 下的源或编译脚本单独列为现有翻译文件，不能冒充原始源脚本；
- `renpy/__init__.py` 只有在不超过 256 KiB 时才读取，并只提取明确的三段
  `version_tuple` 作为非必需版本线索。

报告状态固定为：

- `source_ready`：扫描完整且发现松散源脚本，当前 source-only 流程可以继续；
- `packaged_requires_import`：编译脚本，或得到启动器/运行时佐证的归档，足以确认标准成品结构，
  但当前版本不能继续；
- `uncertain`：只有弱扩展名线索、目录证据不完整，或扫描因权限、链接、深度、数量上限而不完整；
- `not_renpy`：没有足以确认 Ren'Py 的证据。

目录遍历不跟随符号链接或 Windows 目录联接，默认最多 12 层和 50,000 个项目。任何影响完整性的
问题都会阻止 `source_ready`。报告路径按项目内相对路径排序，包含结构化问题代码和明确的
`can_translate_now` 布尔值；它不根据文件名或 Provider 输出给出概率分数。

## 推迟

本增量不解包 RPA、不反编译 RPYc、不处理加密或 DRM、不运行游戏或 SDK、不复制游戏、不创建
工作区或汉化副本，也不增加 CLI、桌面桥、GUI、Provider、网络、翻译、导出或自动启动入口。
Ren'Py 版本线索缺失不单独判为失败，因为许多正常分发不会保留可读的版本声明。

## 结果

GalTrans 现在能在零写入前提下告诉后续界面：输入当前可用、像标准 Ren'Py 成品但尚待导入、证据
不确定，或不是 Ren'Py。自制测试覆盖 source-only、编译加归档成品、现有翻译目录、伪造孤立
归档、运行时残留、扫描上限和输入哈希不变。

代价是“已识别成品”仍不能汉化；它只是把真实兼容性缺口变成稳定、可测试的产品状态。下一增量
应先把报告接入桌面工作台，再为明确支持的非加密标准分发设计独立、可审计的导入边界。
