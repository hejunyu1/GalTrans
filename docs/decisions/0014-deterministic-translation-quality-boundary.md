# 0014：用确定性检查产生可审阅的低置信度译文列表

- 状态：已接受
- 日期：2026-08-25
- 后续：ADR 0015 把质量报告绑定到已完成检查点接受的提案，并在 SQLite v4 中持久化。

## 背景

ADR 0008 至 0013 已经定义结构化译文的来源、标记、恢复、持久化和 Ren'Py 内存导出准备边界。
这些校验可以证明“提案属于当前任务且没有破坏结构”，但不能证明“译文已经翻译”或“语言质量
足够好”。例如 Provider 完整回显原文时，提案可以通过 schema、来源和受保护标记校验，却很可能
是漏译。

未改动的专名、符号和本来无需翻译的文本也可能完全合理，因此第一条质量检查不能把相同文本
判定为结构错误或自动拒绝。V0.3 需要先建立一个确定性、可序列化的低置信度结果边界，让后续
玩家审阅界面能够解释“为什么需要复核”，而不是过早引入无法校准的数值评分。

## 决定

### 输入证据与完整覆盖

`assess_translation_quality` 接收一个 `TranslationTask` 和完整的 `ValidatedTranslation` 集合。
它重新验证任务的关闭式序列化，要求译文完整且唯一覆盖任务，并逐条核对任务、批次、文本段、
来源 SHA-256、目标语言和由完整提案内容计算的 `proposal_` 摘要。输入顺序不影响结果；报告始终
按任务的批次和文本段顺序生成。

`ValidatedTranslation` 必须已经经过当前引擎适配器的结构与受保护标记校验。质量检查不会再次
实现引擎语法解析，也不会把报告变成渲染、导出或发布许可；任何进入这些边界的提案仍须遵守
原有的重新验证要求。

### 版本化质量报告

质量报告 schema 从 1 开始，并采用关闭式字段集合。报告包含任务 ID、实际执行的版本化检查 ID
和每个文本段的结果。结果绑定文本段 ID 与提案 ID，状态只能是：

- `clear`：当前已实现的确定性检查没有发现问题；不表示译文正确、自然或高置信度；
- `low_confidence`：至少有一个结构化问题，需要后续人工或语义审校复核。

每个低置信度结果必须包含至少一个结构化 finding，`clear` 结果不能携带 finding。未知 schema、
检查集合、问题代码、额外字段、重复文本段、重复提案或自相矛盾状态都失败关闭。报告只在内存
返回；本增量不修改 SQLite schema。

### 第一条确定性检查

第一条检查 ID 为 `unchanged_source_text_v1`，问题代码为 `source_text_unchanged`。源文本和目标
文本先分别做 Unicode NFC 规范化；如果结果完全相同，该译文标记为 `low_confidence`。

规则有意不去除首尾空白、不折叠标点、不统计日文或中文字符比例，也不猜测目标语言文字系统。
这使判定可以跨语言稳定复现，并避免把更宽泛的启发式误写成确定事实。它也意味着只增加空白或
少量字符就不会命中本规则；后续检查必须用独立版本和测试扩展，不能把 `clear` 偷换为质量保证。

## 推迟

本增量不实现真实 Provider、网络、凭据、GUI、CLI 翻译入口、质量报告持久化、人工审批状态、
数值置信度或质量评分、术语和角色一致性、目标语言字符比例、语义审校、翻译记忆、审计和费用，
也不自动调用 Ren'Py 渲染器、SDK、磁盘导出或启动验证。

## 结果

GalTrans 现在可以对一个完整、已经过引擎校验的任务生成稳定的结构化质量报告，并把原文未变化
的译文列入可解释的低置信度结果。后续 UI、审计或持久化里程碑可以消费该 schema，而不需要把
Provider 自报分数或自然语言理由当作事实来源。

代价是第一条检查非常保守：它会把合理保留的文本送去复核，也会漏掉大量实际低质量译文。
这种误报和漏报范围必须保持显式，直到更多确定性规则和独立的语义审校边界建立。
