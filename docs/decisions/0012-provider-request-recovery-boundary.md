# 0012：用持久化 Provider 回执恢复在途与模糊失败请求

- 状态：已接受
- 日期：2026-08-24

## 背景

ADR 0011 已为精确筛选批次和 backend identity 定义稳定 `request_` ID，并在完整响应通过当前
引擎验证后保存结果缓存。但请求可能已经到达未来的 Provider，而本地进程在收到或保存响应前
退出。此时缓存为空不能证明服务端没有执行或计费，直接重试会产生重复调用风险。

GalTrans 需要先定义自己拥有的调用回执和恢复状态，再接真实网络、凭据或费用系统。这个增量只
使用确定性替身，不假定某个厂商的会话、幂等期限或计费语义。

## 决定

### 幂等键与 Provider 协议

ADR 0011 的稳定 `request_` ID 同时作为 Provider 幂等键。它继续覆盖请求 schema、完整有序的
筛选 `TranslationBatch` 和显式 backend identity；任何影响输出的配置变化必须使用新的
backend identity。凭据不得进入 identity 或幂等键。

`TranslationBackend` 只提供两个窄操作：

- `submit(batch, idempotency_key)`：提交筛选批次并返回调用回执；
- `query(idempotency_key, provider_request_id)`：按相同幂等键和可选 Provider 引用查询结果。

替身仍不能接收游戏路径、来源行号、SDK、导出位置、Shell 或文件能力。

### 关闭式调用回执

版本化 `ProviderRequestReceipt` 必须回显幂等键，可携带一个不含凭据的受限 Provider 请求引用，
并且状态只能是：

- `in_flight`：Provider 明确确认请求仍在执行；必须有请求引用，不能有提案或错误；
- `succeeded`：Provider 已返回结构化提案；必须有至少一个提案，不能有错误；
- `failed`：Provider 明确确认本次请求失败；不能有提案，必须有错误说明；
- `unknown`：本地无法证明请求是否执行；不能有提案，必须有错误说明。

额外字段、未知版本、无效组合、错误幂等键或不安全的 Provider 引用都失败关闭。成功只表示收到
Provider 响应，不表示提案已被 GalTrans 接受；提案仍须经过任务来源核对和当前引擎标记扫描。

### SQLite v3 与状态更新

SQLite schema 提升为 v3，新增 `translation_provider_requests`。每个稳定请求保存任务、批次、
backend identity、规范筛选批次和最新回执。更新使用现有 `BEGIN IMMEDIATE` 事务与显式旧回执
比较交换，拒绝过期执行者覆盖较新事实。

一旦记录 Provider 请求引用，后续回执不能移除或替换它。成功回执是终态，只允许相同内容幂等
重放；确定失败只有在调用方明确批准重试时才能回到 `unknown`。SQLite v1、v2 和未知版本失败
关闭，不进行当前尚无长期用户数据库需求支撑的迁移。

### 提交、崩溃恢复与重试

执行器在调用 Provider 前先把批次检查点保存为 `running`，再保存一个 `unknown` 回执，最后才
调用 `submit`。本地状态和远端受理无法成为同一事务；预先保存 `unknown` 不能消除该窗口，但能
确保崩溃后不会把“尚无回执”误认为“服务端未执行”。

恢复规则是：

| 已知状态 | 自动动作 | 禁止事项 |
|---|---|---|
| 无回执 | 安全退回暂停；Provider 尚未被调用 | 不猜测已提交 |
| `in_flight` | 按原幂等键查询 | 不创建第二个请求 |
| `succeeded` | 重新验证提案并完成或记录本地验证失败 | 不把回执当成导出许可 |
| `failed` | 记录任务失败；显式恢复后才可同键重试 | 不自动重试 |
| `unknown` | 按原幂等键查询 | 查询不能消歧时不重提，要求人工处理 |

已有已验证结果缓存仍优先用于完成崩溃后的检查点。若成功回执中的提案无效，任务失败且同一成功
终态不能被新响应覆盖；调用方必须人工处理或使用代表真实配置变化的新 backend identity。

## 推迟

本增量不实现真实 Provider、网络、凭据、子进程隔离、超时、取消、用量和费用、预算审批、审计
事件、翻译记忆、缓存淘汰或数据库迁移，也不增加 CLI、GUI、渲染、导出或启动入口。真实 Provider
还必须单独证明其幂等期限、查询保证、数据发送范围和计费行为。

## 结果

GalTrans 现在能用确定性替身证明：稳定请求可以留下严格回执，在途和未知请求能在重开后查询，
确定失败只能受控重试，而无法消歧的请求不会自动产生第二次可能计费的调用。所有成功结果仍是
待验证提案，应用自有 SQLite 状态继续是恢复事实来源。

代价是 SQLite v2 文件不再可打开，执行中的未知请求可能需要人工处理，且只有接入具体服务后才
能验证真实幂等与查询能力；这些限制必须保持显式，不能用“已有回执协议”冒充费用完全去重。
